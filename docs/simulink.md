# Simulink

`simulink/ride_lib.slx` holds the two vehicle models as Simulink blocks, plus the blocks that feed them. The library is generated by `simulink/build_ride_lib.m`; edit the script, not the `.slx`, and run it again after a change to `data/models/*/params.json`.

```matlab
setup                      % also puts simulink/ on the path
open_system('ride_lib')    % or find "Ride models" in the Library Browser
run_demo('halfcar')        % a demo model driven by ride.run's scenario and speeds
```

## Blocks

| Block | Inputs | Outputs |
| --- | --- | --- |
| Quarter-car | `zdot`: road height rate under the wheel [m/s] | `z_B_ddot`, `z_W_ddot` [m/s^2], `x` (5 states) |
| Half-car | `zdot_f`, `zdot_r` [m/s], `a_x` [m/s^2] | `z_B_ddot`, `phi_ddot`, `z_Wf_ddot`, `z_Wr_ddot`, `x` (10 states) |
| Axle | `zdot`, `v_corner`: vertical velocity of the body above the axle [m/s] | `F_s`: suspension force on the body [N], `z_W_ddot`, `x` (3 states) |
| Road | `s`, `v` | `zdot` at a wheel `lag_m` behind the front axle |
| Drive | none | `s`, `v`, `a_x` from a speed sequence |

The vehicle blocks are masked subsystems. Their parameters are mask parameters with the defaults from `params.json`, grouped by body and axle. Inside, the models are plain block diagrams: integrators for the states, gains and sums for the linear forces, and one MATLAB Function block each for the progressive spring and the damper, whose smooth piecewise characteristics are the same code as `ride.core.suspension`. The Quarter-car and the Half-car are built from the same Axle block.

The states in `x`:

- Quarter-car: tyre deflection, wheel velocity, suspension deflection, body velocity, body position.
- Half-car: the three axle states of the rear and then the front axle, body velocity, pitch rate, body position, pitch angle.

The half-car's speed state of `ride.simulate` is not a state here; the speed enters through the Road and Drive blocks.

## Driving a block

The Road block takes a terrain struct, the `road` field of any scenario, so measured and synthetic roads work the same way. The Drive block plays back one speed per step `dt` and holds it over the step, as `ride.simulate` does, and gives `a_x = (v_k - v_(k-1)) / dt` for the half-car's load transfer.

`build_harness(name, vehicle)` wires Drive, Road and a vehicle block into a model that reads four workspace variables:

| Variable | Content |
| --- | --- |
| `ride_road` | terrain struct, for example `r.road` |
| `ride_speeds` | speed at every step [m/s], for example `r.speeds` |
| `ride_dt` | output step, `P.DT` (0.02 s) |
| `ride_dt_sim` | solver step, `P.DT_SIM` (0.001 s) |

The solver is fixed-step `ode4`, the same fourth-order Runge-Kutta with 1 ms steps as the MATLAB code. `ride_demo_halfcar.slx` and `ride_demo_quartercar.slx` are such models with scopes; `build_demo` regenerates them. Their `InitFcn` fills the variables from `ride.run` when they are missing.

## Checks

```matlab
test_quartercar_simulink
test_halfcar_simulink
```

Both replay the reference runs in `data/models/*/reference` through the library blocks and compare every output step. Body heave and pitch, and the wheel accelerations, agree with the reference to about 1e-12 relative to the peak.

One convention differs from `ride.simulate`. At the boundary between two 20 ms steps Simulink evaluates its outputs with the input of the step that starts, while `ride.simulate` reports the step that ends. The two agree wherever the output depends on the states only (body heave acceleration). For outputs that also depend on the input at that instant (pitch acceleration through `a_x`, wheel acceleration through the tyre damping), the tests shift the reference to the Simulink convention with the model's own load-transfer and tyre-damping terms before comparing.
